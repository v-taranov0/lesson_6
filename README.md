# Домашнее задание к уроку №6. Сервисный слой и бизнес-логика

Сервис учёта заказов из прошлого задания уже используют на кассе кофейни. Прошла неделя, и тимлид пишет тебе снова:

> Отличная работа, бариста доволен! К сервису подключаются ещё два разработчика — будете развивать его втроём. Бухгалтерия просит запретить изменение и отмену выполненного заказа: это как чек, его задним числом не переписывают. QA хочет проверять это правило без запуска HTTP-сервера. Разложи код по слоям, как мы сделали на уроке с каталогом товаров.

## Что нужно сделать

Возьми свой сервис из ДЗ 5. Сохрани его эндпоинты и добавь одно правило: после перехода в статус `completed` заказ нельзя ни изменить, ни отменить. Раздели хранение данных, бизнес-логику и обработку HTTP-запросов.

### Repository — слой данных (`repository.py`)

- Опиши класс `OrderRepository`, который хранит список заказов в `self._orders`.
- Реализуй методы `get_all()`, `get_by_id(order_id)`, `add(order)`, `update(order_id, update_data)` и `delete(order_id)`.
- Методы `update` и `delete` выполняют операцию, если заказ найден. Проверка статуса заказа относится к сервисному слою.

### Service — слой бизнес-логики (`service.py`)

- Опиши класс `OrderService`, который получает `OrderRepository` через конструктор.
- Перенеси в сервис операции из прошлого задания: создание заказа, получение по идентификатору, выдачу списка с фильтром по статусу, частичное обновление и отмену.
- При обращении к несуществующему заказу поднимай `OrderNotFoundError`.
- Если заказ **уже** в статусе `completed`, попытка изменить любое его поле или отменить заказ должна вызвать `OrderAlreadyCompletedError`. Проверяй статус сохранённого заказа и для `PATCH`, и для `DELETE`.

### Собственные исключения (`exceptions.py`)

- Объяви `OrderNotFoundError(order_id)` и `OrderAlreadyCompletedError(order_id)` как классы, унаследованные от `Exception`.
- Исключения и сервис должны работать без импорта FastAPI. Преобразование ошибок в HTTP-ответы выполняется в `main.py`.

### Router — слой HTTP (`routers/orders.py`)

- Создай отдельный `APIRouter` с префиксом `/orders` и тегом заказов.
- Каждый эндпоинт разбирает запрос и вызывает один метод сервиса. Поиск в цикле, проверку статуса и обработку бизнес-ошибок вынеси из роутера.
- Оставь `GET /` и `GET /info` в `main.py`: эти эндпоинты относятся ко всему приложению.

### Зависимости (`dependencies.py`)

- Опиши `get_repository` и добавь к нему `@lru_cache`, чтобы заказы в памяти сохранялись между запросами.
- Свяжи `get_service` с `get_repository` через `Depends`. Создай алиас `ServiceDep`, через который эндпоинты будут получать сервис.
- Перенеси сюда `SettingsDep` из прошлого задания.

### Конфигурация (`config.py`)

- Перенеси `Settings` и `get_settings` из прошлого задания. Добавь `@lru_cache` к `get_settings`, чтобы файл `.env` не перечитывался при каждом запросе.

### Обработка ошибок (`main.py`)

- Зарегистрируй два обработчика через `@app.exception_handler`. Для `OrderNotFoundError` возвращай `JSONResponse` со статусом **404**, для `OrderAlreadyCompletedError` — со статусом **409**.
- В обоих случаях передавай пояснение в поле `detail`. Статус 409 означает, что операция конфликтует с текущим состоянием заказа.

### Модели данных (`schemas.py`)

- Перенеси без изменений модели и перечисления из ДЗ 5: `DrinkSize`, `OrderStatus`, `OrderCreate`, `OrderUpdate` и `Order`.

### Сборка приложения (`main.py`)

- Создай приложение `FastAPI(...)`, подключи `orders.router` через `include_router`, оставь сервисные эндпоинты и зарегистрируй оба обработчика ошибок.
- Проверь `/docs` после переноса. Метаданные приложения, теги и `summary` эндпоинтов из ДЗ 5 должны сохраниться.

## Бонус

Пагинация и сортировка — дополнительная часть задания.

- Вынеси `limit` и `offset` в функцию-зависимость `pagination_params`. Создай в `dependencies.py` алиас `PaginationDep` и передавай в роутер `pagination: PaginationDep` вместо двух отдельных параметров.
- Если в ДЗ 5 ты реализовал сортировку заказов, перенеси её из эндпоинта в `OrderService.list_orders`.

## Итоговая структура проекта

```text

├── __init__.py

```

Если выполняешь бонус, добавь `PaginationDep` в `dependencies.py`.

## Дополнительные материалы

Внутри пакета можно использовать относительные импорты. Например, `from .config import Settings` обращается к модулю в том же пакете, а `from ..dependencies import ServiceDep` в файле `routers/orders.py` поднимается на уровень выше. Положи пустой файл `__init__.py` в `app/` и в `app/routers/`.

Запускай сервис из корня проекта, где находится папка `app/`:

```bash
fastapi dev app/main.py
```

Пример структуры приложения и объяснение относительных и абсолютных импортов есть в разделе [Bigger Applications — Multiple Files](https://fastapi.tiangolo.com/tutorial/bigger-applications/) документации FastAPI.

## Ограничения

- Храни заказы в памяти процесса. PostgreSQL и SQLAlchemy появятся в следующем уроке.
- Автоматические тесты на pytest не требуются. Для самопроверки можно создать `OrderRepository()` в Python-консоли, передать его в `OrderService` и вызвать методы сервиса без FastAPI.
- Docker не требуется.
- Названия файлов и глубина вложенности могут отличаться от примера. Важно, чтобы у каждого модуля была понятная зона ответственности.

## Пример

**Изменение выполненного заказа.** Заказ с идентификатором 1 уже получил статус `completed`. Клиент пытается поменять имя:

```http
PATCH /orders/1

{
  "customer_name": "Ирина"
}
```

Ответ со статусом **409 Conflict**:

```json
{
  "detail": "Заказ 1 уже выполнен и не может быть изменён"
}
```

Если заказа с таким идентификатором нет, тот же запрос вернёт **404 Not Found**:

```json
{
  "detail": "Заказ с id=1 не найден"
}
```
